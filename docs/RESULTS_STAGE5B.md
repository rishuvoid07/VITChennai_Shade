## 2. Root Cause Analysis & Reader Layer Fix

### Root Cause of the ZIP Speed Disparity
In Python's `zipfile` module, `ZipFile.open()` returns an instance of `ZipExtFile`. In standard CPython, wrapping `io.TextIOWrapper` directly over `ZipExtFile` without an intermediate binary buffer forces `TextIOWrapper`'s line scanner to issue frequent, unbuffered small-chunk reads (`MIN_READ_SIZE = 4096` or `read1`), repeatedly incurring CPython method dispatch and decompression framing overhead. Plain files opened via `open(path, "r")`, in contrast, benefit directly from C runtime buffered file streams.

### The Fix
In `src/main.py`:
1. For ZIP inputs, the underlying `ZipExtFile` member is wrapped in `io.BufferedReader(bio, buffer_size=65536)` before passing to `io.TextIOWrapper(buf, encoding="utf-8-sig", newline="")`.
2. For plain CSV and directory inputs, files are opened with explicit `buffering=65536`.
3. Strict $O(1)$ memory streaming is preserved: data is processed line-by-line via the generator `row_stream()` without ever buffering whole files into RAM.
4. The estimator equations, constants, filter parameters, and state progression remain completely untouched.

## 5. Standardized Consistent Measurement Results

### Heap Difference Explanation
> **Why the 3-minute heap (2.66 MB) was higher than the 21-minute heap (1.1 MB) in Stage 5:**  
> The Stage 5 3-minute test traced module compilation and AST setup by invoking `runpy.run_path` inside `tracemalloc`, whereas the 21-minute test imported `main` before starting `tracemalloc` and thus measured only the true estimator runtime heap (~1.1 MB).

### Column Definitions
1. **Dataset Input Target**: The evaluated sequence and container format (plain CSV file vs streaming ZIP archive).
2. **Duration (s)**: Total physical flight time represented in the dataset based on timestamps ($t_{\text{end}} - t_{\text{start}}$).
3. **Peak Heap (MB)**: Peak memory allocated by CPython's memory allocator during execution, measured via `tracemalloc` in-process with module loading isolated outside the trace window (budget $\le 8.000$ MB).
4. **In-Proc Time (s)**: Median execution time across 5 in-process runs of `main()` with `tracemalloc` disabled (measuring line parsing, filtering, and disk writing via `perf_counter`).
5. **In-Proc ms/s**: Algorithmic compute cost per 1 second of IMU input ($\text{Time} \times 1000 / \text{Duration}$) (target $\le 10.0$ ms/s).
6. **Subproc Wall (s)**: Median total wall time across 5 CLI subprocess runs (`python src/main.py in out`) including Python interpreter startup and shutdown.
7. **Subproc ms/s**: Overall operating system level processing rate per 1 second of IMU input.
